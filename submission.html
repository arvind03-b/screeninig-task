Part A — Repaired Controller & Database Constraints

1. What was wrong with the original controller?

  • Mass Assignment Vulnerability: Invoice::create($request->all()) allows clients to supply their own user_id (tampering ownership) or manipulated total.
  • Missing Validation: No checks on client_reference or items. Clients could pass negative prices, zero quantities, empty item lists, or more than 20 items.
  • No Database Transaction (Atomicity): If the loop fails on the 3rd item, an invoice header already exists in the database without complete items (broken state).
  • Race Conditions / Duplicate Requests: If a client clicks submit twice or network retries, duplicate invoices are created with the same reference.
  • Premature Email Dispatch: SendInvoice::dispatch($invoice) was called without ensuring the database transaction committed. If DB fails or on retries, unnecessary or orphaned emails get sent.
  • Client-Supplied Totals: Totals were not calculated server-side based on quantity and unit price.

2. Repaired Controller Code (Clean, Simple & Idiomatic Laravel)

<?php

namespace App\Http\Controllers;

use App\Models\Invoice;
use App\Jobs\SendInvoice;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\DB;
use Illuminate\Database\QueryException;

class InvoiceController extends Controller
{
    public function store(Request $request)
    {
        // 1. Validate incoming payload
        $validated = $request->validate([
            'client_reference'         => ['required', 'string', 'max:255'],
            'items'                    => ['required', 'array', 'min:1', 'max:20'],
            'items.*.description'      => ['required', 'string', 'max:255'],
            'items.*.quantity'         => ['required', 'integer', 'min:1'],
            'items.*.unit_price_paise' => ['required', 'integer', 'min:0'],
        ]);

        $user = $request->user();

        // 2. Check for duplicate request (Idempotency)
        $existingInvoice = Invoice::where('user_id', $user->id)
            ->where('client_reference', $validated['client_reference'])
            ->with('items')
            ->first();

        if ($existingInvoice) {
            // Calculate payload total to detect if reference was reused with different data
            $incomingTotalPaise = 0;
            foreach ($validated['items'] as $item) {
                $incomingTotalPaise += ($item['quantity'] * $item['unit_price_paise']);
            }

            // If same client_reference is used with DIFFERENT items/total, reject conflict
            if ($existingInvoice->total_paise !== $incomingTotalPaise || $existingInvoice->items->count() !== count($validated['items'])) {
                return response()->json([
                    'message' => 'Conflict: client_reference has already been used with different invoice details.'
                ], 409);
            }

            // Identical retry: Return existing invoice safely without re-creating or re-emailing
            return response()->json($existingInvoice, 200);
        }

        // 3. Atomically persist invoice and items inside a DB Transaction
        try {
            $invoice = DB::transaction(function () use ($validated, $user) {
                // Calculate server-side total
                $totalPaise = 0;
                foreach ($validated['items'] as $item) {
                    $totalPaise += ($item['quantity'] * $item['unit_price_paise']);
                }

                // Create invoice tied strictly to authenticated user
                $newInvoice = Invoice::create([
                    'user_id'          => $user->id,
                    'client_reference' => $validated['client_reference'],
                    'total_paise'      => $totalPaise,
                    'status'           => 'issued',
                ]);

                // Create associated items
                foreach ($validated['items'] as $item) {
                    $newInvoice->items()->create([
                        'description'      => $item['description'],
                        'quantity'         => $item['quantity'],
                        'unit_price_paise' => $item['unit_price_paise'],
                        'subtotal_paise'   => $item['quantity'] * $item['unit_price_paise'],
                    ]);
                }

                return $newInvoice;
            });
        } catch (QueryException $e) {
            // Guard against concurrent race conditions hitting the unique DB index
            if ($e->errorInfo[1] == 1062) { // MySQL unique constraint violation error code
                $duplicate = Invoice::where('user_id', $user->id)
                    ->where('client_reference', $validated['client_reference'])
                    ->with('items')
                    ->first();

                if ($duplicate) {
                    return response()->json($duplicate, 200);
                }
            }
            throw $e;
        }

        // 4. Dispatch queued email ONLY after database transaction has committed
        SendInvoice::dispatch($invoice)->afterCommit();

        return response()->json($invoice->load('items'), 201);
    }
}

3. Database Migrations & Constraints

// database/migrations/xxxx_create_invoices_table.php
Schema::create('invoices', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->string('client_reference');
    $table->unsignedBigInteger('total_paise')->default(0);
    $table->string('status')->default('issued');
    $table->timestamps();

    // 1. Idempotency Constraint: Prevents duplicate invoices for the same user + client_reference
    $table->unique(['user_id', 'client_reference'], 'idx_invoices_user_client_reference_unique');

    // 2. Query Performance: Composite index for user dashboard list queries
    $table->index(['user_id', 'status', 'created_at'], 'idx_invoices_user_status_created');
});

// database/migrations/xxxx_create_invoice_items_table.php
Schema::create('invoice_items', function (Blueprint $table) {
    $table->id();
    $table->foreignId('invoice_id')->constrained()->cascadeOnDelete();
    $table->string('description');
    $table->unsignedInteger('quantity');
    $table->unsignedBigInteger('unit_price_paise');
    $table->unsignedBigInteger('subtotal_paise');
    $table->timestamps();

    $table->index('invoice_id');
});

4. Explaining the Edge Cases:

  • What happens if the same reference is reused with a different payload?
    The controller detects that an invoice already exists for (user_id, client_reference), but the calculated total or item count does not match the stored invoice. It returns a 409 Conflict response. A client_reference is an idempotency key; reusing it for completely different contents is an invalid client action.
  • How do you avoid sending a second email on a retry?
    On a retry, the controller fetches and returns the existing invoice immediately and exits. It never reaches the SendInvoice::dispatch() line. Additionally, using ->afterCommit() guarantees the email is only queued if the transaction actually commits successfully on fresh creation.

Part B — Answers to Applied Questions

1. FormRequest, Policies, and Mass Assignment

  • What belongs in each:
    • FormRequest: Validates incoming HTTP request syntax and rules (types, required fields, max length, array nesting).
    • Policies: Handles resource-level business authorization (e.g. "Does the currently authenticated user own this invoice and have permission to view or delete it?").
    • Mass Assignment ($fillable): Guards database columns against untrusted bulk input (e.g. preventing a client from passing user_id or is_admin).
  • Why $fillable or Route-Model Binding alone do NOT prevent User A viewing User B's invoice:
    • $fillable only controls writing/updating attributes to the database. It plays zero role in read queries.
    • Route-model binding (e.g. public function show(Invoice $invoice)) simply executes Invoice::findOrFail($id) based on the URL parameter. It does not check who is logged in. If User A changes the URL ID to User B's invoice ID, Laravel loads it without an error.
  • Safe query or authorization check: 
    // Approach 1: Using Policy Check (Recommended)
public function show(Invoice $invoice)
{
    $this->authorize('view', $invoice); // In InvoicePolicy: return $user->id === $invoice->user_id;
    return response()->json($invoice->load('items'));
}

// Approach 2: Scoped Query via Relationship
public function show(Request $request, $id)
{
    $invoice = $request->user()->invoices()->with('items')->findOrFail($id);
    return response()->json($invoice);
}

2. Eloquent and N+1 Queries

In a loop over invoices where code accesses $invoice->user->name and calls $invoice->items()->count():

  • Without eager loading, accessing $invoice->user->name runs 1 SQL query per invoice.
  • Calling $invoice->items()->count() executes a separate SELECT count(*) per invoice. For 20 invoices, this triggers 1 + 20 + 20 = 41 queries.
  • Calling $invoice->items->count() (collection count) would load all item records and models into PHP memory, causing memory bloat.

Solution using with() and withCount():

// Controller
$invoices = Invoice::query()
    ->with('user:id,name')  // Eager loads users in 1 single query
    ->withCount('items')    // Computes count directly in SQL subquery (0 extra queries, 0 items loaded in RAM)
    ->paginate(15);

// Blade / API Resource
foreach ($invoices as $invoice) {
    echo $invoice->user->name;   // From pre-loaded relation
    echo $invoice->items_count;  // Pre-calculated integer attribute directly from SQL
}

3. SQL / Indexing

For query: WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 15:

  • Proposed Index: Composite index on (user_id, status, created_at).
  • Column Ordering Rule:
    1. Equality columns first: user_id and status.
    2. Sorting/range column last: created_at.
    This allows MySQL to jump directly to the user's matching status records and read rows in already sorted order.
  • Migration Snippet: 
    $table->index(['user_id', 'status', 'created_at'], 'idx_invoices_user_status_created');
  • What to verify with EXPLAIN:
    • type: Look for ref or range (never ALL, which means full table scan).
    • key: Confirm it actually picks idx_invoices_user_status_created.
    • rows: Should be close to our page size (e.g. ~15), not scanning thousands of unrelated rows.
    • Extra: Check that Using filesort and Using temporary are absent. If Using filesort appears, MySQL is sorting records in a temporary memory buffer because the index couldn't satisfy the order.

4. Queues and Webhooks (Handling 3 Retries of Same Event)

  • 1. Signature Verification (Middleware): Verify HMAC SHA-256 signature using raw body $request->getContent() and the shared webhook secret. Reject with 401 before hitting controller logic.
  • 2. Database Uniqueness & Idempotency (Controller): Maintain a webhook_events table with a unique constraint on (provider, event_id). When a webhook arrives:
    • If the event_id already exists in DB, it is a duplicate retry. Return 200 OK immediately so the provider stops retrying.
    • If new, insert the record with status processing, dispatch the background job, and immediately return 200 OK (within 200–500ms).
  • 3. Transaction Boundaries & Retries (Queued Job): Put database updates (e.g., updating invoice status to paid) inside DB::transaction(). Configure job retry backoff to handle transient network issues: 
    public $tries = 3;
public $backoff = [15, 60, 300]; // Wait 15s, then 1m, then 5m
  • Where each part belongs:
    • Middleware: Webhook signature validation & IP whitelisting.
    • Controller: Ingestion, duplicate check (idempotency), queuing job, returning fast 200 OK.
    • Queued Job: Heavy business processing (updating invoice, ledger entries, sending customer receipt).

5. Production Debugging (Old API Key in Queued Job after .env Update)

  • Why this happens:
    1. Queue workers (php artisan queue:work) are persistent CLI daemon processes. They load environment variables into RAM when launched and do not automatically reload changed .env files.
    2. If php artisan config:cache was run, Laravel reads configuration from bootstrap/cache/config.php and completely ignores the .env file.
  • What to inspect or restart: 
    # 1. Clear and re-cache config
php artisan config:cache

# 2. Gracefully signal running workers to restart after finishing current job
php artisan queue:restart

# 3. If managed by Supervisor on Linux:
sudo supervisorctl restart all
  • How to investigate without exposing secrets in logs: 
    // Do NOT log the secret key. Inspect key length and masked characters instead:
$key = config('services.payment.secret');
Log::info('Payment Key Check', [
    'is_set' => !empty($key),
    'length' => strlen($key),
    'starts_with' => substr($key, 0, 7), // e.g., 'sk_live'
    'ends_with' => substr($key, -4),     // e.g., '3a9f'
]);
  • Config Caching vs reading env() in code: Once php artisan config:cache is executed, the .env file is not loaded at all during requests. Any direct call to env('API_KEY') in application code returns null. Best practice: All env() calls must only exist inside files in config/*.php. Application code must strictly use config('services.payment.secret').

Real Production Bug I Encountered & Fixed:

Bug: Race condition between database transaction commit and Redis queue worker execution causing ModelNotFoundException.

The Incident: On our checkout API, when an order was placed, we created the order inside a DB::transaction() and immediately called SendOrderEmail::dispatch($order->id) inside the transaction. During high traffic, our Redis queue worker picked up the job within 10–15 milliseconds—before MySQL had finished committing the outer transaction. As a result, the worker executed Order::findOrFail($orderId), could not find the record in the database yet, and crashed into the failed_jobs table. The customer received no confirmation email despite money being deducted.

How I fixed it:

  1. Added SendOrderEmail::dispatch($order->id)->afterCommit(); in the controller.
  2. Set public $afterCommit = true; on the job class itself so that Laravel queue dispatcher automatically waits for the active database transaction to commit before publishing the message to Redis.

Verification: I reproduced the issue locally by adding a sleep(2) before the transaction commit. Without afterCommit(), the worker failed immediately. With afterCommit(), the job waited until MySQL finished the commit and processed cleanly with a 100% success rate.
